# 📦 ملی اکشن — Meli-Action

**ابزاری مبتنی بر گیت‌هاب اکشن برای دور زدن فیلترینگ اینترنت — دانلود فایل از لینک مستقیم، یوتیوب، تلگرام، گوگل پلی، و ذخیره صفحات وب، همه از طریق سرورهای فیلتر نشده گیت‌هاب.**


---

## 🌐 چطور کار می‌کنه؟

گیت‌هاب اکشن‌ها روی سرورهای خود گیت‌هاب اجرا می‌شن که **توسط فیلترینگ اینترنت ملی ایران بلاک نشدن**. این پروژه از همین موضوع استفاده می‌کنه:

- **برای دانلود فایل:** ورک‌فلو با `curl` فایل را در runner دانلود و به آرشیو 7z تبدیل می‌کند؛ سپس آن را در ریپازیتوری یا یک GitHub Release ذخیره می‌کند.
- **برای آرشیو صفحات وب:** یک مرورگر بی‌سر Chromium (از طریق `playwright`) صفحه فیلتر شده رو کامل رندر می‌کنه، به فرمت MHTML ذخیره می‌کنه، زیپش می‌کنه و به ریپازیتوری پوش می‌کنه.
- **برای یوتیوب، تلگرام و گوگل پلی:** ورک‌فلوهای اختصاصی از ابزارها و سرویس‌های مستقل استفاده می‌کنند. خروجی معمولاً در `downloads/` و آرشیو MHTML در `download/` ذخیره می‌شود.

هیچ نرم‌افزاری نیاز نیست روی دستگاه شما نصب بشه. همه چیز در فضای ابری اجرا می‌شه.

## 🚀 شروع به کار

### مرحله ۱ — فورک کن

دکمه **Fork** رو در بالای صفحه بزن تا ریپازیتوری وارد حساب گیت‌هاب خودت بشه.

### مرحله ۲ — مجوز نوشتن اکشن‌ها رو فعال کن

ورک‌فلوها برای کامیت کردن فایل‌های دانلود شده به ریپازیتوری شما نیاز به مجوز دارن:

۱. توی ریپازیتوری فورک شده، برو به **Settings** ⚙️.
۲. از منوی سمت چپ، برو به **Actions → General**.
۳. زیر بخش **"Workflow permissions"**، گزینه **"Read and write permissions"** رو انتخاب کن.
۴. **Save** رو بزن.

> **همچنین**، زیر بخش **"Actions permissions"**، مطمئن بشو که **"Allow all actions and reusable workflows"** انتخاب شده.

> ⚠️ **امنیت:** مجوز نوشتن، کد ورک‌فلو و ابزارهای شخص ثالث را قادر به تغییر ریپازیتوری می‌کند. فقط ورک‌فلوها و لینک‌های مورد اعتماد را اجرا کنید و از ذخیره اطلاعات محرمانه در خروجی یا لاگ خودداری کنید.

### مرحله ۳ — یک ورک‌فلو اجرا کن

۱. به تب **Actions** توی ریپازیتوری خودت برو.
۲. ورک‌فلوی مورد نظرت رو از لیست سمت چپ انتخاب کن (مثلاً «دانلود از URL»، «دانلودر یوتیوب» و غیره).
۳. دکمه **Run workflow** رو بزن.
۴. پارامترهای لازم رو وارد کن (مثل URL، کیفیت ویدیو، پوشه خروجی).
۵. دکمه سبز **Run workflow** رو بزن.

بعد از اتمام اجرا، هر دانلود در پوشه‌ای با نام خودش داخل مسیر خروجی (معمولاً `downloads/`) ذخیره می‌شود و همهٔ قسمت‌هایش همان‌جا قرار می‌گیرند. مثلاً `downloads/video.mp4/video.7z.001`. آرشیو صفحات نیز داخل زیرپوشه‌ای در `download/` قرار می‌گیرد. نام تکراری با پسوند `(2)` و ... پوشهٔ تازه می‌گیرد و دانلود قبلی بازنویسی نمی‌شود. فایل‌های قدیمی جابه‌جا نمی‌شوند.

GitHub Release از پوشه برای assetها پشتیبانی نمی‌کند؛ در حالت Release، فایل‌ها مانند قبل به‌صورت asset جداگانهٔ همان Release منتشر می‌شوند.

## ⚙️ جزئیات فنی

### دانلودر لینک مستقیم
از `curl` و `7z` استفاده می‌کند. برای انتشار در ریپازیتوری اندازه هر قسمت باید بین ۱ تا ۹۵ MiB و برای Release بین ۱ تا ۱۹۰۰ MiB باشد. برای استخراج چندقسمتی، همه قسمت‌ها را کنار هم قرار دهید و قسمت اول را با 7-Zip باز کنید. GitHub فایل‌های بزرگ‌تر از ۱۰۰ MiB را در Git عادی رد می‌کند؛ نگهداری فایل‌های بزرگ در تاریخچه Git اندازه clone را افزایش می‌دهد.

### فشرده‌سازی و پارت‌بندی
آرشیوهای 7z در سطح Ultra (`-mx=9`) با دیکشنری محدودشده به ۶۴ MiB و حداکثر دو thread برای کنترل مصرف حافظه ساخته می‌شوند. آرشیوهای ZIP با Deflate سطح ۹ ساخته می‌شوند تا فرمت و روش استخراج قبلی حفظ شود. این فشرده‌سازی **بدون افت کیفیت** است: فایل استخراج‌شده دقیقاً با نسخهٔ اصلی یکسان خواهد بود. در ورک‌فلوهایی که تقسیم اختیاری است، فایل‌های کوچک‌تر از آستانه همچنان بدون آرشیو می‌مانند و در دانلودرهایی که این گزینه را دارند، مقدار صفر تقسیم را غیرفعال می‌کند.

میزان کاهش به محتوای فایل بستگی دارد؛ برای متن و دادهٔ تکراری ممکن است زیاد باشد، اما ویدئو، موسیقی، APK و فایل‌های فشردهٔ موجود معمولاً کاهش اندکی دارند یا حتی آرشیو کمی بزرگ‌تر می‌شود. تبدیل قطعی ۳ گیگابایت به ۱ گیگابایت یا کمتر تضمین‌شدنی نیست. فشرده‌سازی قوی‌تر به زمان و حافظهٔ بیشتری نیاز دارد؛ از قبل جا برای فایل اصلی و آرشیو روی runner در نظر بگیرید. کاهش شدید ویدئو معمولاً به تبدیل مجدد با افت کیفیت نیاز دارد و این پروژه آن را بدون درخواست صریح انجام نمی‌دهد.

برای استخراج ZIP چندقسمتی، همهٔ فایل‌های `.z01`، `.z02` و فایل نهایی `.zip` باید در یک پوشه باشند؛ با 7-Zip یا برنامهٔ سازگار با ZIP چندقسمتی باز کنید. برای 7z چندقسمتی نیز تمام قسمت‌ها را کنار هم گذاشته و فایل `.7z.001` را باز کنید.

### آرشیوکننده صفحات وب (`save_as_mhtml.py`)
از کتابخانهٔ Python `playwright` برای راه‌اندازی یک نمونه Chromium بی‌سر استفاده می‌کنه، به URL مورد نظر می‌ره، صبر می‌کنه تا صفحه کامل لود بشه و بعد در فرمت MHTML ذخیره‌اش می‌کنه. آرشیو نهایی زیپ شده و به ریپازیتوری کامیت می‌شه.

### دانلودر یوتیوب
ورک‌فلوی پیشرفته از `yt-dlp` و ورک‌فلوی ساده از سرویس تبدیل شخص ثالث استفاده می‌کند و از انتخاب کیفیت (مثل ۷۲۰p، ۱۰۸۰p، فقط صدا) پشتیبانی می‌کنه. فایل `google_service.json` رو می‌شه توی v2ray ایمپورت کرد تا جستجو و مرور تامبنیل‌های یوتیوب در یک پروکسی ممکن بشه.

### دانلودر عمومی yt-dlp (قبلاً دانلودر محتوای بزرگسالان)
ورک‌فلوی «دانلودر عمومی ویدئو (yt-dlp)» لینک HTTP(S) یا شناسهٔ ویژهٔ معتبر yt-dlp را بدون فهرست ثابت دامنه به yt-dlp می‌سپارد؛ بنابراین علاوه بر PornHub، می‌تواند از [سایت‌های پشتیبانی‌شدهٔ yt-dlp](https://github.com/yt-dlp/yt-dlp/blob/master/supportedsites.md) و استخراج‌کنندهٔ عمومی استفاده کند. در هر اجرا جدیدترین نسخهٔ **پایدار منتشرشده در PyPI** با `--upgrade` نصب و نسخه در لاگ ثبت می‌شود؛ سایت‌هایی که بعداً به نسخهٔ پایدار اضافه شوند، خودکار در اجراهای بعدی در دسترس‌اند. فهرست شاخهٔ master ممکن است جلوتر از نسخهٔ پایدار باشد. Node.js، ابزار JS مورد نیاز YouTube، ffmpeg و `curl_cffi` نیز نصب یا فعال می‌شوند. نصب وابستگی‌های به‌روز نیازمند دسترسی به PyPI است و تغییر نسخه ممکن است رفتار را تغییر دهد.

لینک و در صورت نیاز `quality` (انتخاب‌گر فرمت yt-dlp) را وارد کنید. حالت پیش‌فرض بهترین ویدئوی دارای ارتفاع مشخص تا سقف ۷۲۰p را انتخاب می‌کند؛ اگر ۷۲۰ موجود نباشد از ۴۸۰ یا کیفیت پایین‌تر موجود استفاده می‌شود. اگر ویدئوی واجد شرایط موجود نباشد، ممکن است فقط صدا انتخاب شود؛ برای انتخاب دیگر می‌توانید `quality` را تغییر دهید. کانتینر MP4 تحمیل نمی‌شود. گزینهٔ `download_playlist` برای لینکی است که هم ویدئو و هم پلی‌لیست را مشخص می‌کند؛ در صورت غیرفعال بودن، ویدئوی تکی ترجیح داده می‌شود. خود لینک پلی‌لیست یا استخراج‌کننده‌ای که چند فایل برمی‌گرداند ممکن است حتی در حالت غیرفعال چند فایل دانلود کند. هر فایل در پوشهٔ خودش ذخیره می‌شود و فایل بزرگ‌تر از ۹۹ MiB به پارت‌های 7z تقسیم می‌شود. پلی‌لیست‌های بزرگ زمان و فضای زیادی لازم دارند و می‌توانند حجم تاریخچهٔ Git را افزایش دهند.

گزینهٔ `upload_method` را می‌توانید روی `repository` یا `release` بگذارید. پس از دانلود، اگر مجموع حجم فایل‌های کامل یک اجرا به **۱ GiB یا بیشتر** برسد، حتی با انتخاب `repository` به‌صورت خودکار `release` استفاده می‌شود؛ این آستانهٔ محافظه‌کارانه پیش از فشرده‌سازی محاسبه می‌شود تا از محدودیت ۲ GiB هر push فاصله داشته باشد. انتخاب صریح `release` برای هر اندازه‌ای رعایت می‌شود. زیر این آستانه، انتخاب `repository` فایل‌ها را در `output_folder` commit می‌کند؛ با وجود این محافظ، خطای push یا تداخل اجرای هم‌زمان همچنان ممکن است. فایل‌های Release با یک `git push` حجیم به تاریخچهٔ Git اضافه نمی‌شوند. Release یک نام یکتا برای هر اجرا دارد؛ ابتدا به‌صورت draft ساخته و فقط پس از آپلود کامل منتشر می‌شود. اگر آپلود شکست بخورد، draft ناقص ممکن است باقی بماند؛ آن را بررسی یا حذف و اجرا را تکرار کنید. Release عمومی در مخزن عمومی برای همه قابل مشاهده است.

دارایی‌های Release تخت هستند و پوشه ندارند؛ در مجموعه‌های چندفایلی، پیشوند شماره‌دار و فایل `yt-dlp-collection-manifest.json` مشخص می‌کنند کدام پارت‌ها متعلق به هر فایل‌اند. برای استخراج، همهٔ پارت‌های یک آرشیو را در یک پوشه گذاشته و قسمت `.7z.001` آن را باز کنید. هر Release حداکثر ۱۰۰۰ دارایی دارد و هر دارایی باید کوچک‌تر از ۲ GiB باشد؛ حجم کل Release، فضای runner و مدت اجرای اکشن همچنان محدودیت‌های عملی دارند.

برای محتوایی که حساب مجاز لازم دارد، در Settings → Secrets and variables → Actions یک repository secret به نام `YTDLP_COOKIES` شامل متن فایل کوکی با فرمت Netscape قرار دهید؛ کوکی موقت با دسترسی محدود ساخته و پس از مرحله پاک می‌شود. از حساب خودتان و محتوایی که اجازهٔ دریافت آن را دارید استفاده کنید. کوکی را در URL یا ورودی عادی قرار ندهید؛ لاگ‌ها و اطلاعات حساب را خصوصی نگه دارید و در صورت لو رفتن، نشست را باطل کنید.

پشتیبانی yt-dlp به معنی موفقیت تضمینی همهٔ لینک‌ها نیست: سایت‌ها تغییر می‌کنند و ممکن است محدودیت IP یا منطقه، ورود، اشتراک، DRM، challenge یا خطای 403 داشته باشند. DRM دور زده نمی‌شود و ممکن است سایت یا فرمت خاص با نسخهٔ پایدار فعلی کار نکند. شناسه‌های ویژه مانند `ytsearch:` تنها در صورت شناسایی توسط استخراج‌کننده‌های نسخهٔ نصب‌شده پذیرفته می‌شوند؛ مسیر فایل محلی و URL پروتکل‌های غیر HTTP(S) برای امنیت مجاز نیستند.

### دانلودر تلگرام
فقط کانال‌های **عمومی** تلگرام رو هدف قرار می‌ده. لینک پست به سرویس شخص ثالث `telegramdownloader.net` فرستاده می‌شود؛ این سرویس API رسمی تلگرام نیست و ممکن است تغییر کند یا در دسترس نباشد. هنگام پاسخ 403، `yt-dlp` ویدئوی یک پست عمومی را از صفحهٔ embed تلگرام امتحان می‌کند؛ این مسیر فایل‌های غیر ویدئویی و محتوای خصوصی را تضمین نمی‌کند.

### دانلودر گوگل پلی
از `gplay-apk-downloader` استفاده می‌کند. این ابزار دیگر توزیع‌کننده توکن پیش‌فرض ندارد؛ قبل از اجرا یک توزیع‌کننده تحت کنترل خودتان را در secret ریپازیتوری با نام `GPLAY_DISPENSER_URL` تنظیم کنید. خروجی split به‌صورت آرشیو منتشر می‌شود؛ حالت ادغام تنها یک APK با امضای معتبر را می‌پذیرد. APK ادغام‌شده با کلید debug امضا می‌شود و ممکن است جایگزین نسخه رسمی نشود یا به‌روزرسانی نگیرد. ابزار بالادستی ممکن است نشانی dispenser را در لاگ چاپ کند؛ به لاگ‌ها دسترسی محدود بدهید.

### نکات مهم اجرا و حریم خصوصی

- لینک‌ها و محتوای قابل دانلود ممکن است برای سرویس‌های شخص ثالث قابل مشاهده باشند؛ از لینک‌های خصوصی یا دارای توکن استفاده نکنید. دانلودر ساده یوتیوب و تلگرام به سرویس‌های بیرونی وابسته‌اند و تغییر یا اختلال آن‌ها می‌تواند اجرا را متوقف کند.
- ورودی `extra_args` در دانلودر پیشرفتهٔ یوتیوب عمداً گزینه‌های قدرتمند yt-dlp (از جمله اجرای دستور) را می‌پذیرد؛ فقط ورودی مورد اعتماد را استفاده کنید.
- Spotify با `spotDL` فراداده را با یک منبع صوتی دیگر تطبیق می‌دهد، نه اینکه فایل اصلی Spotify را دریافت کند؛ کیفیت واقعی به منبع و محدودیت سرویس بستگی دارد.
- ورودی `zip_password` و کوکی ورودی محرمانه نیستند و ممکن است در تاریخچه یا لاگ اجرا دیده شوند. کوکی یوتیوب را به‌جای ورودی در secret به نام `YT_COOKIES` قرار دهید. برای آرشیوهای بسیار حساس به این ورودی رمز تکیه نکنید.
- مسیر خروجی باید نسبی، داخل ریپازیتوری و بدون اجزای مخفی یا `..` باشد. انتشار در Git فقط برای شاخهٔ انتخاب‌شده مجاز است، نه اجرای workflow روی tag. چند اجرای هم‌زمان ممکن است هنگام push با هم تداخل کنند؛ در صورت خطای non-fast-forward اجرا را تکرار کنید. برای Release، نام tag تکراری ممکن است دارایی‌های موجود را جایگزین کند؛ از tag یکتا استفاده کنید.
- برای `max_part_mb` در ورک‌فلوهای انتشار به ریپازیتوری حداکثر ۹۵ MiB مجاز است؛ در دو دانلودر تلگرام و یوتیوب پیشرفته مقدار صفر تقسیم را غیرفعال می‌کند، ولی فایل بیش از ۱۰۰ MiB همچنان قابل push نیست.

### اجرای تست‌ها

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install requests pyyaml
python -m unittest discover -s tests -v
python scripts/check_workflows.py
```

برخی تست‌ها به `ffmpeg`، `7z`، `zip` و `yt-dlp` نیاز دارند و در نبود آن‌ها رد می‌شوند. برای اجرای تست واقعی Chromium، ابتدا `python -m pip install playwright` و `python -m playwright install chromium` را اجرا کنید، سپس با `MELI_TEST_BROWSER=1 python -m unittest discover -s tests -v` تست بگیرید. CI این ابزارها و Chromium را نصب می‌کند. تست‌ها همچنین سرویس تلگرام را شبیه‌سازی می‌کنند و جایگزین اجرای واقعی ورک‌فلوها در GitHub و آزمودن سرویس‌های بیرونی نیستند.
